# OrderFlow

[English](README.md) | [Русский](README.ru.md)

OrderFlow — проект системы обработки заказов с прицелом на эксплуатацию в production, предназначенный для демонстрации инженерных навыков Middle+/Senior Go Backend Developer. Разработка начинается с сервиса заказов; будущие сервисы будут находиться в одном monorepo. Решение: [ADR 001](docs/adr/001-monorepo.ru.md).

В проекте есть один исполняемый файл, структурированное JSON-логирование, команды разработки, CI и протестированный домен заказов. Домен проверяет заказы и позиции, реализует подтверждение, завершение и отмену, включая повторные действия. Операции приложения и хранение ещё не реализованы; сетевого сервера, базы данных и брокера нет. Приложение по-прежнему записывает сообщение о запуске и успешно завершает работу.

## Цели

- Построить понятную и поддерживаемую систему обработки заказов с явными границами модулей.
- Изучить транзакционную согласованность, надёжную доставку событий и идемпотентную обработку.
- По мере добавления функциональности продемонстрировать тестирование, наблюдаемость и практики эксплуатации.
- Выделять отдельные сервисы только при наличии конкретных требований, оправдывающих дополнительную сложность.

## Быстрый старт

Необходимы Go 1.27.3 или новее, Git и Make. CI использует версию из `go.mod`. Для тестов с детектором гонок также нужны CGO и компилятор C, например clang на macOS или GCC на Linux.

```sh
git clone https://github.com/CatMacales/OrderFlow.git
cd OrderFlow
make run
```

Ожидаемый результат — JSON-лог со значением `OrderFlow foundation initialized` в поле `msg` и `orderflow` в поле `service`. Затем процесс завершается с кодом 0.

```sh
make build       # Собрать bin/orderflow
make test        # Запустить тесты
make test-race   # Запустить тесты с детектором гонок
make fmt         # Отформатировать Go-пакеты
make vet         # Выполнить статический анализ
make generate    # Запустить генераторы кода
```

Если Go установлен вне PATH, укажите путь к исполняемому файлу явно, например `make GO=/path/to/go build`.

Переменные окружения и внешние сервисы пока не требуются, поэтому `.env.example` не добавлен. Доменные тесты покрывают валидацию, все 12 сочетаний состояния и действия, неизменность данных заказа и владение срезом позиций. CI проверяет форматирование, сборку, выполняет vet и тесты с детектором гонок.

ID заказа использует `github.com/google/uuid`; домен принимает ненулевой UUID v4 с вариантом RFC 4122. `quantity` имеет тип `int64` и должен быть положительным. Внешние ID покупателя и товара сохраняются точно. Конструкторы проверяют данные; состояние меняют методы заказа. `Items()` возвращает копию.

Статусы генерируются закреплённым инструментом `go-enum` из `internal/order/domain/status.go`. После изменения объявления enum выполните:

```sh
make generate
```

Храните `status_enum.go` в репозитории и не редактируйте вручную. Обычная сборка использует этот файл без запуска генератора. Флаги SQL-интеграции не включены; будущие преобразования для хранения относятся к адаптеру хранилища.

## Структура проекта

```text
cmd/orderflow/       Точка входа приложения
internal/           Внутренние пакеты, добавляемые по мере необходимости
internal/order/domain/ Модель заказа, проверка позиций, жизненный цикл и тесты
api/proto/          Будущие контракты Protocol Buffers
migrations/         Будущие SQL-миграции
docs/adr/           Записи об архитектурных решениях
deploy/             Будущая конфигурация развёртывания
.github/workflows/  Непрерывная интеграция
```

Зарезервированные каталоги содержат только `.gitkeep`. Архитектурные слои без конкретной необходимости не создаются.

## План развития

Правила работы с заказами: [требования](docs/order-requirements.ru.md) и [приёмочные примеры](docs/order-acceptance.ru.md). Доменные правила реализованы и протестированы; полные сценарии приложения, хранение в памяти и запускаемая демонстрация остаются задачами этапа 2.

1. Определить первый сценарий обработки заказа, инварианты, жизненный цикл и границы модулей; описать ключевые компромиссы в ADR.
2. Реализовать и протестировать минимальный сквозной сценарий с явным внедрением зависимостей и передачей контекста.
3. Добавить хранение данных в PostgreSQL, миграции Goose и запросы SQLC с интеграционными тестами.
4. Добавить gRPC API, валидацию запросов, ограничения времени выполнения и корректное завершение приложения.
5. Добавить Transactional Outbox и публикацию в Kafka с повторными попытками и идемпотентными потребителями.
6. Развить наблюдаемость, тестирование сбоев и документацию по развёртыванию.

Каждый этап должен давать работающий результат до добавления следующей инфраструктуры или абстракций.
