# Order requirements

[English](order-requirements.md) | [Русский](order-requirements.ru.md)

Accepted by the user: 2026-10-27. Stage 1 complete.

## Scope and boundaries

Build the order service in a monorepo ([ADR 001](adr/001-monorepo.md)). The customer places orders directly; no operator or separate created_by field is needed. The service owns order data and lifecycle rules. Product catalog and customer profiles are external responsibilities.

The first version has no product names, prices, currency, totals, payments, inventory, shipping, or order editing. It does not authenticate callers, enforce customer/store permissions, or verify external object existence. Customer and store are business roles only; authentication and authorization are deferred. This is an explicit first-version limitation.

Use in-memory storage in stage 2. Orders do not survive process restart. PostgreSQL and restart durability checks belong to stage 3.

## Data

| Field | Source | Rule |
| --- | --- | --- |
| order_id | Generated by OrderFlow | UUID v4; empty, malformed, and nil input order_id are invalid |
| customer_id | Creation request | Required nonempty external string; no UUID or other format check |
| status | OrderFlow | created initially; transitions below |
| items | Creation request | At least one line |
| items[].product_id | Creation request | Required nonempty external string; unique within the order |
| items[].quantity | Creation request | Positive integer |

Preserve external strings exactly: no trimming, case conversion, or normalization. Duplicate product detection uses exact string equality; duplicate lines are rejected rather than merged. A line contains product_id and quantity only.

No arbitrary business upper limits on quantities or line count are introduced. Numeric representation and range handling are implementation decisions; request-size limits belong to the API stage.

## State meanings

- created: the customer has placed and thereby confirmed the order; it awaits store acceptance and is not a draft.
- confirmed: the store has accepted the order for processing.
- completed: the order is completed.
- cancelled: the order is cancelled.

There is no separate customer confirmation operation.

## Operations

| Operation | Input | Successful response |
| --- | --- | --- |
| CreateOrder | customer_id, items | Newly generated order_id; stored state is created |
| GetOrder | order_id | Complete order with lines and current state |
| ConfirmOrder | order_id | Success without order body |
| CompleteOrder | order_id | Success without order body |
| CancelOrder | order_id | Success without order body |

Success does not necessarily mean state changed. Agreed repeated actions succeed without changes. Retrieval is available in every state and changes nothing.

## Transition matrix

| Current state | Store confirmation | Complete | Cancel |
| --- | --- | --- | --- |
| created | Success → confirmed | INVALID_ORDER_STATE | Success → cancelled |
| confirmed | Success, unchanged | Success → completed | Success → cancelled |
| completed | Success, unchanged | Success, unchanged | INVALID_ORDER_STATE |
| cancelled | INVALID_ORDER_STATE | INVALID_ORDER_STATE | Success, unchanged |

Reverse transitions are not allowed. State actions do not change customer or lines. Failed actions leave orders unchanged.

## Errors

| Application code | Cause | Planned gRPC mapping |
| --- | --- | --- |
| INVALID_ARGUMENT | Invalid order_id, empty external ID, empty items, nonpositive quantity, duplicate product | InvalidArgument |
| ORDER_NOT_FOUND | Valid order_id with no matching order | NotFound |
| INVALID_ORDER_STATE | Action forbidden in the current state | FailedPrecondition |

Errors have recognizable codes and explanatory messages. Failed creation stores no order. Get and state actions on a missing order return ORDER_NOT_FOUND. Wire format and gRPC mapping implementation belong to the API stage.
