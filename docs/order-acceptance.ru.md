# Приёмочные примеры для заказов

[English](order-acceptance.md) | [Русский](order-acceptance.ru.md)

Черновик критериев приёмки. Это спецификация будущих тестов, а не результаты их выполнения.

Правила: [требования](order-requirements.ru.md). Архитектура: [ADR 001](adr/001-monorepo.ru.md).

Принято пользователем: 2026-10-27.

## Создание и получение

Дано: customer_id = `customer-42`; две позиции: product_id = `SKU-MUG`, quantity = 2 и product_id = `catalog:notebook:7`, quantity = 1.

Когда: создаём заказ. Тогда: возвращается новый order_id в формате UUID. Получение по этому ID возвращает тот же customer_id, обе позиции с исходными количествами и статус created. Вызовы внешних сервисов не требуются.

## Переходы

Каждая ячейка — отдельный пример. Дано: существующий заказ в статусе строки. Когда: выполняем действие столбца. Тогда: получаем указанный результат и проверяем состояние отдельным получением заказа. Покупатель и позиции не меняются.

| Исходный статус | Подтвердить магазином | Завершить | Отменить |
| --- | --- | --- | --- |
| created | Успех, confirmed | INVALID_ORDER_STATE, created | Успех, cancelled |
| confirmed | Успех, confirmed | Успех, completed | Успех, cancelled |
| completed | Успех, completed | Успех, completed | INVALID_ORDER_STATE, completed |
| cancelled | INVALID_ORDER_STATE, cancelled | INVALID_ORDER_STATE, cancelled | Успех, cancelled |

Получение из каждого из четырёх статусов возвращает заказ без изменений. Успех действий над статусом не содержит тело заказа.

## Некорректные данные

Каждый случай проверяется отдельно; ожидается INVALID_ARGUMENT, новый заказ не сохраняется:

- Пустой список позиций.
- quantity = 0.
- quantity = -1.
- Две позиции с одним product_id, даже при разных количествах: автоматического объединения нет.

Для получения, подтверждения, завершения и отмены с некорректным order_id ожидается INVALID_ARGUMENT; существующие заказы не меняются.

## Отсутствующий заказ

Дано: корректный UUID, отсутствующий в хранилище. Получение, подтверждение, завершение и отмена по этому UUID по отдельности возвращают ORDER_NOT_FOUND.

## Срок хранения

Первая версия хранит заказы в памяти и теряет их при перезапуске. Постоянное хранение и проверки сохранности после перезапуска относятся к этапу PostgreSQL.

## Согласованные границы проверок

Позиции содержат только product_id и quantity, без названия. Аутентификация и авторизация не входят в первую версию; бизнес-роли не означают проверку полномочий. Произвольные бизнес-лимиты не вводим. Числовой тип определяется при реализации, размер запроса — на этапе API. Проверки постоянного хранения, конкурентных изменений и создания с ключом идемпотентности относятся к последующим этапам.

## Идентификаторы заказов

Создание со строками customer-42, SKU-MUG и catalog:notebook:7 допустимо: UUID для внешних ID не требуется. Генерируемый order_id — UUID v4. Получение, подтверждение, завершение и отмена с пустым order_id или нулевым UUID возвращают INVALID_ARGUMENT без изменений заказов.

## Проверки внешних строковых ID

- Пустой customer_id: INVALID_ARGUMENT, заказ не создаётся.
- Пустой product_id любой позиции: INVALID_ARGUMENT, заказ не создаётся.
- Непустые внешние ID после создания и получения совпадают с переданными строками, включая регистр и пробелы.
- Повтор точно совпадающего product_id в двух позициях: INVALID_ARGUMENT. Разные строки не объединяются посредством нормализации.
